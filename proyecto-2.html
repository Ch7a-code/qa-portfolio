Urban Grocers API — Pruebas de endpoints REST con Postman

Sprint 4 · TripleTen QA Engineer · 2026 · API Testing · Postman · Jira

Contexto del proyecto

Urban Grocers es la API REST de un e-commerce de abarrotes. El reto del Sprint 4 era pasar del testing de UI al testing de contratos de API: leer la documentación Swagger, diseñar casos por endpoint, ejecutar con Postman y reportar defectos en Jira con la información que un desarrollador necesita para reproducir.

Mi rol: QA Manual Jr — análisis de spec OpenAPI, diseño y ejecución de 41 casos de prueba, reporte de 16 defectos en Jira con criterios de aceptación.

2. Tipos de prueba aplicados a la API

  • Validación de schema: el body de respuesta cumple el contrato Swagger (campos obligatorios, tipos correctos)
  • Códigos HTTP esperados: 200/201 en éxito, 400 en payload inválido, 401 sin token, 404 en recurso inexistente
  • Boundary testing: nombre de kit con 0, 1, 2, 511, 512 caracteres
  • Negative testing: tipos incorrectos (string donde se espera int), campos faltantes, headers ausentes
  • Idempotencia: repetir POST y verificar duplicados o conflicto

Conclusiones

  • API testing es más rápido y más profundo que UI testing. 41 casos en 2 días, mientras que la misma cobertura desde UI tomaría una semana y dependería de timing del front.
  • Schema-first me ahorra discusiones. Si la spec dice quantity: integer, no hay debate: el bug es claro y el dev no puede negarlo.
  • El bug crítico (UG-3) lo encontré en negative testing, no en flujo positivo. Confirma que probar lo que no debería pasar tiene más ROI que probar lo obvio.
  • Lo que mejoraría: automatizar los 41 casos en una colección Postman con scripts de aserciones (pm.test) para correrlos en CI. Lo construyo en Sprint 6.
